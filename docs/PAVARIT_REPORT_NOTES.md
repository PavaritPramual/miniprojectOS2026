# บันทึกส่วนรายงานของปวริศช์

เอกสารนี้รวบรวมส่วนที่ปวริศช์ทำ ใช้เป็นร่างสำหรับรวมในรายงานกลุ่ม ผลที่ยังไม่ได้ลองกับโปรแกรม C จริงระบุไว้ตามตรง วิธีเปิดและส่งต่ออยู่ใน [คู่มือส่วนปวริศช์](PAVARIT_HANDOFF.md) ตั้งแต่ 5 ตุลาคม 2569 ใช้ระบบ C → Python → เว็บแนวทางเดียว ตัดงาน benchmark เปรียบเทียบและการวัดหน่วยความจำออก

## หน้าที่ในงาน

ปวริศช์ทำส่วน Python ที่รับรายการไฟล์จากโปรแกรม C เก็บผลใน SQLite คำนวณยอดรวมของโฟลเดอร์ และส่งรายการให้หน้าเว็บขอทีละหน้า ส่วนหน้าเว็บและโปรแกรม C เป็นงานของสมาชิกอีกสองคน

## การทำงานของส่วน Python

1. หน้าเว็บส่งคำขอเริ่มอ่านโฟลเดอร์
2. Python สร้างงานเบื้องหลัง จึงตอบหน้าเว็บได้โดยไม่ต้องรอการอ่านไฟล์จบ
3. โปรแกรม C ส่งข้อมูลออกมาทีละบรรทัด; Python ตรวจตำแหน่ง ชนิดรายการ และขนาดก่อนเก็บลง SQLite เป็นชุด ๆ
4. สำหรับไฟล์จริงบน Windows Python ใช้ `GetCompressedFileSizeW` วัดพื้นที่ที่ไฟล์ใช้บนดิสก์
5. เว็บขอสถานะ รายการลูกครั้งละไม่เกิน 50 รายการ หรือรายการที่อ่านไม่ได้/ข้ามได้
6. root บันทึกทันที ข้อมูลที่ตามมาบันทึกทุก 128 รายการหรือทุก 1 วินาที แม้โปรแกรมส่งข้อมูลเงียบชั่วคราว ขณะอ่านใช้ลำดับที่รับ เมื่อจบจึงเรียงตามพื้นที่
7. การยกเลิกส่งคำสั่งหยุดไปยัง PID ใน Ubuntu และตรวจว่าหยุดจริง ถ้ายืนยันไม่ได้ภายใน 15 วินาทีแสดง failed พร้อมเหตุผล
8. ผลจริงล่าสุดเปิดกลับได้จาก `/api/scans/latest?path=...` หลังปิด/เปิดเซิร์ฟเวอร์ ผลตัวอย่างไม่ทับผลจริง

ข้อมูลตัวอย่างต้องเลือก `source: "sample"` เองเสมอ หากไม่ได้ตั้งโปรแกรม C ไว้ การเริ่มอ่านจริงจะแจ้งข้อผิดพลาด ไม่เปลี่ยนไปใช้ข้อมูลสมมติเอง

## ความหมายของขนาด

- **Logical Size** คือจำนวนไบต์ของเนื้อหาไฟล์ที่โปรแกรมอ่านได้
- **Allocated Size** คือจำนวนไบต์ที่ Windows รายงานว่าไฟล์ใช้บนดิสก์
- ขนาดโฟลเดอร์รวมจากไฟล์ที่อ่านได้ข้างใน ถ้าอ่านหรือวัดรายการใดไม่ได้ให้ทำเครื่องหมายผลบางส่วน และใช้ `null` แทนค่าที่ไม่ทราบ
- ผลรวมของไฟล์ไม่จำเป็นต้องเท่ากับพื้นที่ที่ Windows รายงานว่าใช้ทั้งไดรฟ์ เพราะอาจมีข้อมูลระบบและรายการที่อ่านไม่ได้
- งานนี้ไม่คำนวณ Slack Space จากการลบตัวเลขสองค่านี้ เพราะไฟล์บีบอัดหรือ sparse ทำให้ผลต่างไม่ใช่ Slack Space เสมอ

## ผลที่ตรวจได้

| รายการตรวจ | ผล |
| --- | --- |
| Fixture สำหรับทดสอบ | มี 64 ไฟล์และ 13 โฟลเดอร์เมื่อนับ root; มีชื่อไทย โฟลเดอร์ลึก 8 ชั้น ไฟล์ว่าง ไฟล์ 1 MiB และโฟลเดอร์ที่มีลูก 60 รายการ |
| รับข้อมูลและรวมผลใน Python | ป้อนรายการที่สร้างจาก fixture ผ่านตัวตรวจและ SQLite ได้ 64 ไฟล์/13 โฟลเดอร์; เป็นการทดสอบส่วนรับข้อมูล ไม่ใช่ผลจากโปรแกรม C |
| ข้อมูลข้ามชุดบันทึก | รับครบทั้ง 130 และ 10,000 ไฟล์ ตรวจทุกหน้าแล้วไม่มีรายการหายหรือซ้ำ |
| โฟลเดอร์เกินจำนวนที่จำไว้ | รับ 1,100 โฟลเดอร์ใต้ root แล้วรับไฟล์ในโฟลเดอร์แรกต่อได้ ใช้ฐานข้อมูลค้นโฟลเดอร์แม่ที่ถูกเอาออกจากรายการที่จำไว้ |
| การแบ่งหน้า | โฟลเดอร์ 60 รายการได้หน้า 50 และ 10 ไม่มีชื่อซ้ำหรือหาย |
| วัดไฟล์ 1 MiB | Windows API รายงาน Allocated Size ของ `large.bin` เป็น 1,048,576 ไบต์; ยังไม่ได้เทียบกับโปรแกรม Windows อื่น |
| วัดรายการที่หาย | ได้ `null` พร้อมสถานะผลบางส่วน ไม่แทนค่าที่วัดไม่ได้ด้วยศูนย์ |
| API ผ่าน localhost | เริ่มข้อมูลตัวอย่างได้ `202`; อ่านสถานะ รายการลูก และ issues ได้ `200`; หน้าหลักเปิดได้ `200` |
| ปัญหาและการยกเลิก | ตรวจข้อมูลผิดรูปแบบ ข้อมูลซ้ำ ข้อมูลจบก่อนมี record `done` และจำนวนท้ายงานผิด ยกเลิกงานที่ยังรอเริ่มและเริ่มงานใหม่ได้ |
| การส่งข้อมูลผ่าน Ubuntu | โปรแกรมจำลองส่ง NDJSON ตาม fixture ผ่าน WSL จริง Python วัดพื้นที่จากไฟล์ Windows จริงและรับครบ 64 ไฟล์/13 โฟลเดอร์ โปรแกรมจำลองไม่ได้เดินโฟลเดอร์เอง |
| การหยุดโปรแกรมใน Ubuntu | ยกเลิกโปรแกรมจำลองที่ส่งช้า เงียบ และไม่รับ TERM ได้ภายใน 15 วินาที ตรวจ PID แล้วหยุดจริง และเรียกงานใหม่ได้ |
| Python พบปัญหาระหว่างรับข้อมูล | ทดสอบให้ส่วนรับข้อมูลหยุดด้วยข้อผิดพลาด โปรแกรมจำลองใน Ubuntu ถูกหยุดด้วยวิธีเดียวกัน |
| ดูผลระหว่างทำงาน | ตรวจการบันทึกขณะโปรแกรมส่งข้อมูลเงียบชั่วคราวและการตอบ HTTP status/cancel ระหว่างงานยังไม่จบ |
| เปิดผลเก่า | ตรวจการเปิดฐานข้อมูลใหม่ การค้นผลจริงล่าสุด และผลตัวอย่างไม่ลบผลจริง; งานค้างจากเซิร์ฟเวอร์รอบก่อนแสดง failed/partial |
| คำขอพร้อมกัน | เซิร์ฟเวอร์สร้างตัวจัดการสแกนเพียงตัวเดียวเมื่อมีหลายคำขอเริ่มพร้อมกัน การขอยกเลิกไม่ทับสถานะงานที่จบไปแล้ว |
| Reveal และข้อจำกัด | ตรวจการตอบกลับสำหรับรายการที่มีอยู่ รายการถูกลบ และ path ที่ไม่อยู่ในผล; การเปิด Explorer ในการทดสอบถูกจำลอง ไม่ได้เปิดหน้าต่างจริง |
| งานสแกนทั้งไดรฟ์ | ตรวจการปฏิเสธเมื่อมีงานทั้งไดรฟ์อีกงานค้าง; ยังไม่ได้สแกนไดรฟ์จริง |

การทดสอบใช้ Python 3.12.14 และ Windows เครื่องนี้ มีทั้งการรับข้อมูลตัวอย่างผ่าน Python และการส่งข้อมูลจากโปรแกรมจำลองใน Ubuntu ผ่าน WSL จริง จึงยืนยันส่วนเชื่อม WSL การรับข้อมูล การรวมผล การวัด Windows และการหยุด PID ของโปรแกรมจำลองได้ ยังไม่ยืนยันโปรแกรม C ของศรัณย์ ชุดตรวจรับรันซ้ำได้ด้วย `python tools/run_checks.py --wsl` และมีหลักฐานล่าสุดใน [ผลทดสอบ](results/backend-tests.txt)

ผลวันที่ 4 ต.ค. ผ่าน **21 ข้อ** รวมการตรวจเครื่องมือ benchmark ด้วยโปรแกรมจำลอง เก็บไว้เป็น [หลักฐานย้อนหลัง](results/archive/backend-tests-2026-10-04.txt) หลังถอดข้อทดสอบ benchmark แล้ว ให้ดูจำนวนและผลชุดปัจจุบันจาก [ผลล่าสุด](results/backend-tests.txt)

## การตรวจงานรอบปัจจุบัน

ตรวจว่ารับข้อมูลครบ ขนาดรวมถูกต้อง แสดงข้อผิดพลาดตรงกับสิ่งที่เกิด ยกเลิกแล้วหยุดจริง และเว็บยังใช้ได้ระหว่างสแกน ไม่มีการเปรียบเทียบกับต้นแบบ ไม่มีการเก็บรายการต่อวินาทีหรือหน่วยความจำ คง `elapsedSeconds` ไว้ให้ผู้ใช้เห็นว่างานทำมาแล้วนานเท่าไร

ผลตรวจ Python/API และโปรแกรมจำลอง WSL ใช้ฐานข้อมูลแยกจากผลใช้งานจริง ส่วนหน้าเว็บใหม่ merge แล้วและมี [หลักฐาน UI](UI_TEST_REPORT.md) การตรวจด้วยข้อมูลสมมติหรือโปรแกรมจำลองไม่ใช่หลักฐาน C จริง

ผลรอบวันที่ 5 ต.ค. ผ่าน **20 ข้อ** บน Windows รวม WSL ไม่มีข้อข้าม ตรวจคำสั่งเปิดโปรแกรมแบบ `-CheckOnly` แล้ว ลองเว็บใหม่กับ Python HTTP และ SQLite ชั่วคราวผ่านข้อมูลตัวอย่างจาก API จริงได้ 64 ไฟล์/13 โฟลเดอร์ ยอด root เท่ากับ Logical 1,048,645 ไบต์ และ Allocated จำลอง 1,302,528 ไบต์ โฟลเดอร์ `many` ได้ 50+10 รายการไม่ซ้ำ และ `empty` แสดง 0 B

ลองงานที่มีปัญหา 60 รายการและงาน failed ที่เตรียมในฐานทดสอบแล้ว เว็บแสดงเหตุผลผ่าน `/issues` และ `status.error` งานที่กำลังทำแสดงกำลังคำนวณ/ไม่ทราบ ไม่แทนด้วยศูนย์ ไม่พบ JavaScript console error ระหว่างลอง เมื่อไม่ได้ตั้ง C เซิร์ฟเวอร์ตอบ `SCANNER_NOT_CONFIGURED` โดยไม่สลับไปข้อมูลตัวอย่าง ผล API และบันทึกสิ่งที่ลองอยู่ใน [หลักฐาน Python กับเว็บ](results/python-web-check.json)

## ผลหลังต่อ C จริง วันที่ 6 ต.ค. 2569

รับ C จาก PR #3 แล้ว build และติดตั้งใน Ubuntu ต่อเข้ากับ Python บน Windows และตรวจจากเว็บปกติ ผลต่อไปนี้เป็นข้อมูลจริง ไม่ใช่ sample หรือ mock:

- รับครบ 64 ไฟล์/13 โฟลเดอร์จาก fixture บนไดรฟ์ D; แบ่งลูก 60 รายการเป็น 50+10 และเว็บแสดงครบ
- ยอด Logical root 1,048,645 ไบต์ตรงกับผลรวมไฟล์จริง Allocated root บนเครื่องนี้ได้ 1,048,645 ไบต์; zero.bin และ large.bin ตรงกับ Windows API อีกวิธีหนึ่ง
- junction ย้อนกลับแสดง skipped / symlink และ partial โดยไม่วนซ้ำ เว็บเปิดดูเหตุผลได้
- สแกนไดรฟ์ D ระหว่างใช้งานเว็บแล้วกดยกเลิกได้ ชุดตรวจยืนยัน PID ของ C หยุดและเริ่มงานใหม่ได้ ไม่ได้รอจนจบทั้งไดรฟ์
- ชุด Windows ผ่าน 24 ข้อ ข้าม C tests 11 ข้อซึ่งรันใน Ubuntu แยกผ่านแล้ว; เพิ่มเทสต์ C จริงผ่าน HTTP 3 ข้อ และเทสต์ root ระหว่างรอ C
- แก้ Python ให้เปิด root ได้ระหว่างรอข้อมูล และแก้ encoding สคริปต์สร้าง fixture เพื่อให้ชื่อไทยถูกต้องใน Windows PowerShell

รายละเอียด วิธีตรวจซ้ำ ภาพ และข้อจำกัดอยู่ใน [ผลการรวมระบบ](results/REAL_SCANNER_INTEGRATION.md) ผลทดสอบและข้อความ “ยังไม่ตรวจ C” ในส่วนวันที่ 4–5 ต.ค. ด้านบนเป็นหลักฐานย้อนหลัง สถานะปัจจุบันให้ใช้ผลวันที่ 6 ต.ค. นี้

ไม่มีข้อกำหนดให้วัดหรือกล่าวอ้างความเร็วของโปรแกรม C รายงานเน้นสถาปัตยกรรม คำสั่ง OS ฟีเจอร์ ความถูกต้อง และข้อจำกัด
