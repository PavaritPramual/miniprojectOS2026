## 📚 หมวดที่ 1: พจนานุกรมคำศัพท์เทคนิคระบบปฏิบัติการ (OS Glossary)

เพื่อให้ทุกคนในกลุ่มเข้าใจศัพท์เทคนิคตรงกัน และนำไปใช้อธิบายได้อย่างถูกต้อง:

| คำศัพท์เทคนิค | ความหมายระดับระบบปฏิบัติการ | ความหมายแบบเข้าใจง่าย |
| :--- | :--- | :--- |
| **Cluster (หรือ Allocation Unit)** | หน่วยการจัดสรรของระบบไฟล์บน volume หนึ่ง ๆ; ขนาดจริงขึ้นกับการจัดรูปแบบ volume | **"ขนาดห้อง/กล่องมาตรฐาน"** เช่น volume NTFS บางลูกใช้ 4,096 ไบต์ แต่ต้องตรวจค่าจริง |
| **Logical Size (EOF)** | ปริมาณข้อมูลจริงที่โปรแกรมเขียนลงในไฟล์ มีค่าเท่ากับตำแหน่งไบต์สุดท้ายของข้อมูล (End-of-File) | **"ขนาดเนื้อไฟล์จริง"** เช่น เขียนตัวหนังสือ 50 ตัว ก็มีขนาด 50 ไบต์ |
| **Allocated Size (Size on Disk)** | จำนวนไบต์ที่ระบบไฟล์รายงานว่าจัดสรรให้ไฟล์; อาจต่างจาก Logical เมื่อมี compression หรือ sparse data | **"พื้นที่ที่ระบบรายงานว่าจองให้ไฟล์"** เวอร์ชันส่งงานต้องวัดจาก Windows API ไม่ใช้สูตรปัด cluster ของต้นแบบ |
| **Internal Fragmentation** | สภาวะที่พื้นที่ภายในคลัสเตอร์ที่ได้รับการจัดสรร มีขนาดใหญ่กว่าขนาดของข้อมูลจริง ทำให้มีพื้นที่ว่างในคลัสเตอร์สุดท้ายที่สูญเปล่าไป | **"พื้นที่สูญเปล่าในกล่องสุดท้าย"** ที่ไม่มีใครเอาไปใช้ต่อได้ |
| **Slack Space** | ในตัวอย่างไฟล์ไม่บีบอัดแบบง่าย อาจประมาณจากขนาดจัดสรรลบขนาดเนื้อหาได้ แต่สูตรนี้ไม่ครอบคลุม compressed/sparse file | **แนวคิดการเรียน** ไม่แสดงเป็นค่าจริงในเวอร์ชันส่งงาน |
| **$MFT (Master File Table)** | โครงสร้างฐานข้อมูลเชิงระบบของระบบไฟล์ NTFS ที่ทำหน้าที่เป็นสารบัญหลัก เก็บเมทาดาตาของทุกไฟล์และไดเรกทอรีบนไดรฟ์ | **"สมุดทะเบียนราษฎร์ของฮาร์ดดิสก์"** ที่บันทึกข้อมูลทุกอย่างของไฟล์ |
| **MFT Record** | ระเบียน metadata ใน NTFS; ขนาดและการใช้พื้นที่ขึ้นกับ volume/การจัดรูปแบบ | **"บัตรข้อมูลของไฟล์"** โดยตัวอย่างในบทเรียนอาจใช้ 1 KB |
| **Resident Attribute** | NTFS อาจเก็บเนื้อหาไฟล์ไว้ในระเบียน MFT เมื่อมีพื้นที่พอ; ไม่มีเกณฑ์ 600 ไบต์ที่ใช้ได้กับทุกไฟล์ | **"ไฟล์เล็กที่อาจอยู่ใน metadata"** ต้องวัดก่อนอ้างขนาดจัดสรร |
| **Non-Resident Attribute** | เนื้อหาที่เก็บนอกระเบียน MFT โดยจัดสรรหน่วยของ volume | **"ไฟล์ที่ต้องใช้พื้นที่นอก metadata"** ขนาด allocation unit ต้องตรวจจริง |
| **Reparse Point** | วัตถุขยายในระบบไฟล์ NTFS ที่มีข้อมูลแท็กพิเศษ (Reparse Tag) กำกับ เพื่อให้ไดรเวอร์ระบบไฟล์สั่งเบี่ยงเส้นทางการเข้าถึง (เช่น Junctions, Symlinks) | **"ประตูกล / ทางลัดเสมือน"** ที่ชี้ข้ามไปโฟลเดอร์อื่น |
| **Directory Junction** | ทางลัดระดับระบบไฟล์ที่เชื่อมโยงไดเรกทอรีหนึ่ง ไปยังไดเรกทอรีเป้าหมายอื่นในเครื่องเดียวกัน | **"ประตูมิติข้ามโฟลเดอร์"** ที่สร้างขึ้นในระดับ OS |
| **Infinite Recursion Loop** | สภาวะที่การท่องโครงสร้างไดเรกทอรีวิ่งวนซ้ำในวงจรไม่รู้จบ จากการที่ Junction หรือ Symlink ชี้กลับไปยังโฟลเดอร์แม่ | **"ลูปนรก"** เดินวนอยู่ในเขาวงกตจนหน่วยความจำล้นและโปรแกรมพัง |
| **Protection Rings (Ring 3 vs Ring 0)** | กลไกความปลอดภัยระดับสถาปัตยกรรม CPU ที่แบ่งแยกระดับสิทธิ์การทำงาน: **Ring 3 (User Mode)** สำหรับโปรแกรมทั่วไป และ **Ring 0 (Kernel Mode)** สำหรับแกนระบบปฏิบัติการ | **"เขตประชาชน (Ring 3) กับ เขตหวงห้ามของรัฐบาล (Ring 0)"** |
| **System Call (Syscall)** | อินเทอร์เฟซส่วนต่อประสานที่อนุญาตให้โปรแกรมใน User Mode ร้องขอรับบริการจาก Kernel Mode | **"การยื่นเรื่องผ่านเคาน์เตอร์ราชการ"** เพื่อขอให้ OS ทำงานแทน |
| **Context Switch** | กระบวนการที่ CPU สลับการทำงานจากโหมดหนึ่งไปยังอีกโหมดหนึ่ง (เช่น Ring 3 $\leftrightarrow$ Ring 0) ซึ่งมีค่าใช้จ่าย CPU ในการบันทึกและโหลดรีจิสเตอร์ | **"ค่าเสียเวลาในการสลับหน้างานของซีพียู"** |
| **I/O Bound** | ลักษณะของภาระงานที่ความเร็วการทำงานถูกจำกัดด้วยความเร็วในการรับ-ส่งข้อมูลของอุปกรณ์จัดเก็บข้อมูล (ไม่ใช่ความเร็วซีพียู) | **"งานที่ซีพียูนั่งรอฮาร์ดดิสก์ส่งของมาให้"** |
| **Queue Depth (QD)** | จำนวนคำสั่งการอ่าน/เขียนข้อมูลที่กำลังรอประมวลผลอยู่ในคิวของตัวควบคุมอุปกรณ์จัดเก็บข้อมูล (Storage Controller) | **"ความยาวของคิวคำสั่งที่ส่งไปให้ฮาร์ดดิสก์ทำพร้อมกัน"** |
| **Producer-Consumer Pattern** | รูปแบบการออกแบบระบบแบบคู่ขนาน โดยมีฝั่งผู้ผลิต (Producer) ป้อนงานเข้าคิว และฝั่งผู้บริโภค (Consumer/Worker) หยิบงานไปทำพร้อมๆ กัน | **"ระบบหัวหน้าจ่ายงานลงตะกร้า แล้วคนงาน 8 คนช่วยกันหยิบไปทำ"** |
| **Global Interpreter Lock (GIL)** | กลไกภายในของไพทอนที่จำกัดให้รันเธรดคำนวณไพทอนได้ทีละ 1 เธรด แต่จะถูกปลดล็อกโดยอัตโนมัติเมื่อเรียกฟังก์ชัน C ระดับต่ำ | **"กุญแจล็อคเธรดของไพทอน"** ที่จะปลดออกเมื่อส่งงานให้ Windows C-API |

### เสาหลักที่ 1: กลไกการจัดสรรพื้นที่ระดับคลัสเตอร์ และคณิตศาสตร์ Slack Space
*(อ้างอิง: หนังสือ Silberschatz บทที่ 14 หัวข้อ 14.4 Allocation Methods)*

#### 1.1 ที่มาเชิงวิศวกรรม:
โครงสร้างฮาร์ดแวร์จัดเก็บข้อมูลแบ่งพื้นที่ทางกายภาพออกเป็น **Sectors** (มาตรฐานดั้งเดิมคือ 512 ไบต์ หรือ 4,096 ไบต์ในมาตรฐาน Advanced Format) หากระบบปฏิบัติการกำหนดให้อ้างอิงที่อยู่ระดับไบต์หรือเซกเตอร์เดี่ยว ขนาดของโครงสร้างดัชนีจะใหญ่เกินขอบเขตที่หน่วยความจำรองรับได้  
ระบบไฟล์ NTFS จึงจัดกลุ่มเซกเตอร์หลายตัวเข้าด้วยกันเป็น **Cluster (Allocation Unit)** โดยดึงข้อมูลได้ผ่าน Win32 API:
$$\text{Cluster Size} = \text{SectorsPerCluster} \times \text{BytesPerSector}$$
บน NTFS มาตรฐาน ค่าดีฟอลต์คือ $8 \times 512 = 4,096 \text{ Bytes (4 KB)}$

#### 1.2 สมการคำนวณ Physical Allocation & Slack Space:
เมื่อมีไฟล์ขนาดเชิงตรรกะ $S_{logical}$ ใดๆ ระบบปฏิบัติการจะต้องจัดสรรคลัสเตอร์จำนวนเต็มคลัสเตอร์ให้แก่ไฟล์นั้น:
$$S_{physical} = \left\lceil \frac{S_{logical}}{S_{cluster}} \right\rceil \times S_{cluster}$$
$$S_{slack} = S_{physical} - S_{logical}$$

#### 1.3 ปรากฏการณ์จริงที่พิสูจน์ได้:
* **ไฟล์วิดีโอ 1 ไฟล์ขนาด 4 GB:** ใช้ประมาณ 1,000,000 คลัสเตอร์ มีเศษเหลือในคลัสเตอร์สุดท้ายสูญเปล่าไม่เกิน $4,095 \text{ B}$ (สูญเปล่าคิดเป็น $< 0.0001\%$)
* **โฟลเดอร์ `.git` หรือ `node_modules` (ไฟล์ขนาด 200 ไบต์ จำนวน 50,000 ไฟล์):**
  * $S_{logical} = 50,000 \times 200 \text{ B} \approx 10 \text{ MB}$
  * $S_{physical} = 50,000 \times 4,096 \text{ B} \approx 204.8 \text{ MB}$
  * **Slack Space ที่สูญเปล่า:** $204.8 - 10 = 194.8 \text{ MB}$ (**พื้นที่สูญเปล่าคิดเป็นกว่า 95.1%!**)

### เสาหลักที่ 2: สถาปัตยกรรมภายใน NTFS MFT และ Resident Files
*(อ้างอิง: หนังสือ Silberschatz บทที่ 14 หัวข้อ 14.1 File-System Structure & 14.4 Indexed Allocation)*

```text
โครงสร้างระเบียน MFT Record (ขนาดคงที่ 1,024 ไบต์):
┌────────────────┬──────────────────────┬──────────────────────┬──────────────────────┐
│  Record Header │ $STANDARD_INFO       │ $FILE_NAME           │ $DATA Attribute      │
│  (Magic 'FILE')│ (Timestamp, Attr)    │ (ชื่อไฟล์ UTF-16)    │                      │
│  ~48 Bytes     │ ~72 Bytes            │ ~100 Bytes           │                      │
└────────────────┴──────────────────────┴──────────────────────┴──────────────────────┘
                                                                ▲
                                                                │
     ┌──────────────────────────────────────────────────────────┴────────────────────────────────┐
     │ กรณี A: Resident Data (ขนาดไฟล์ ≤ 600B)                                                  │
     │ └─ [เนื้อหาข้อมูลจริงของไฟล์ถูกบันทึกในช่องนี้โดยตรง!] ──> Physical On-Disk Clusters = 0 Bytes │
     ├──────────────────────────────────────────────────────────────────────────────────────────┤
     │ กรณี B: Non-Resident Data (ขนาดไฟล์ > 600B)                                               │
     │ └─ [เก็บเป็น Data Runs / Extents ชี้พิกัด LCN ไปยังคลัสเตอร์ 4KB ภายนอกดิสก์]              │
     └──────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 2.1 โครงสร้างของ Master File Table ($MFT):
ระบบไฟล์ NTFS ไม่ใช้โครงสร้าง Inode เหมือน Unix/Linux แต่ใช้ **MFT Record ขนาด 1,024 ไบต์** ในการบันทึกแอตทริบิวต์ทุกอย่างของไฟล์  
แอตทริบิวต์หลักประกอบด้วย:
1. `$STANDARD_INFORMATION`: เก็บเวลาสร้าง วันที่แก้ไข และบิตสถานะความปลอดภัย
2. `$FILE_NAME`: เก็บชื่อไฟล์ในรหัสอักขระ UTF-16
3. `$DATA`: เก็บข้อมูลเนื้อหาจริงของไฟล์

#### 2.2 Resident vs Non-Resident Attribute:
* **Resident Attribute:** เมื่อเนื้อหาไฟล์มีขนาดเล็กพอที่จะแทรกลงในช่องว่างที่เหลืออยู่ของ MFT Record 1,024 ไบต์นั้นได้ ไดรเวอร์ NTFS จะไม่จัดสรรคลัสเตอร์ภายนอกเลย ส่งผลให้ **Logical Size มีค่าตามข้อมูล แต่ Physical Allocation บนคลัสเตอร์ภายนอกมีค่าเท่ากับ 0 ไบต์อย่างสมบูรณ์**
* **Non-Resident Attribute:** เมื่อไฟล์มีขนาดเกินความจุของระเบียน MFT ไดรเวอร์จะจัดสรรคลัสเตอร์ภายนอก แล้วบันทึกพิกัดของคลัสเตอร์ในรูปของ **Data Runs (Extents)** โดยแปลงจาก Virtual Cluster Number (VCN) ไปเป็น Logical Cluster Number (LCN)

### เสาหลักที่ 3: โครงสร้างต้นไม้ และกลไกตรวจจับ Reparse Points
*(อ้างอิง: หนังสือ Silberschatz บทที่ 13 หัวข้อ 13.3 Directory Implementation)*

```text
ตัวอย่างการเกิด Infinite Recursion Loop:
C:\Project\
    ├── src\
    └── backup_link\  ──(Directory Junction ชี้วนกลับ)──┐
            ▲                                            │
            └────────────────────────────────────────────┘
ผลลัพธ์ถ้าไม่ดักจับ: C:\Project\backup_link\backup_link\backup_link\... (RAM ล้น และ Crash)
```

#### 3.1 ความท้าทายของ Directed Graph Traversal:
ไดเรกทอรีทั่วไปมีสถานะเป็น Directed Acyclic Graph (DAG) แต่การมีอยู่ของ **Directory Junctions (Mount Points)** และ **Symbolic Links** บน NTFS ทำให้โครงสร้างกลายเป็น General Graph ที่มีวงวน (Cycles) ได้

#### 3.2 การดักจับเชิงระบบในระดับเคอร์เนล:
ในการสำรวจระเบียน `WIN32_FIND_DATAW` ระบบจะทำการตรวจสอบสถานะผ่านบิตมาสก์:
```c
if (find_data.dwFileAttributes & FILE_ATTRIBUTE_REPARSE_POINT) {
    // โหนดนี้เป็น Junction หรือ Symlink
    // ปฏิบัติต่อโหนดนี้เป็น Leaf Node ทันที และห้ามท่องโครงสร้างเข้าไปข้างใน
}
```
แท็กในระเบียน `dwReserved0` จะระบุประเภทอย่างชัดเจน:
* `IO_REPARSE_TAG_MOUNT_POINT` (ค่า `0xA0000003`): Directory Junction
* `IO_REPARSE_TAG_SYMLINK` (ค่า `0xA000000C`): Symbolic Link  
การข้าม reparse point ช่วยลดความเสี่ยงการเดินวนของต้นแบบ แต่ต้องทดสอบ junction/symlink จริงก่อนอ้างว่าป้องกันได้ครบทุกกรณี

### เสาหลักที่ 4: สถาปัตยกรรม I/O Concurrency และความลึกของคิว NVMe SSD
*(อ้างอิง: หนังสือ Silberschatz บทที่ 4 Threads & บทที่ 12 I/O Systems)*

#### 4.1 ความแตกต่างระหว่าง HDD และ NVMe SSD:
* **Hard Disk Drive (HDD):** มีหัวอ่านทางกลไกเพียงชุดเดียว หากรับคำสั่งหลายช่องทางพร้อมกัน จะเกิดปัญหา Head Thrashing ทำให้ค่า Latency พุ่งสูง ดังนั้นสถาปัตยกรรมเดิมจึงทำงานที่ Queue Depth = 1
* **NVMe Solid State Drive (SSD):** ขจัดข้อจำกัดทางกลไกทั้งหมด เชื่อมต่อผ่านบัส PCIe ตรงเข้าสู่ CPU รองรับการทำงานแบบ Multi-channel NAND Flash Controller และมาตรฐาน NVMe กำหนดให้รองรับ **Submission Queue ได้สูงสุดถึง 64,000 คิว โดยแต่ละคิวบรรจุคำสั่งได้ 64,000 คำสั่งพร้อมกัน**

#### 4.2 ทำไม `os.walk` ถึงทำให้ SSD ทำงานได้ต่ำกว่าศักยภาพจริง?
`os.walk` ทำงานแบบเธรดเดี่ยวแบบซิงโครนัส (Synchronous Blocking I/O):
$$\text{Scan Directory } A \longrightarrow \text{Wait I/O} \longrightarrow \text{Process} \longrightarrow \text{Scan Directory } B \longrightarrow \text{Wait I/O}$$
ส่งผลให้ค่า **Queue Depth ($QD$) มีค่าเท่ากับ 1 อยู่ตลอดเวลา** อุปกรณ์จัดเก็บข้อมูลความเร็วสูงจึงตกอยู่ในสภาวะคิวคำสั่งว่างเปล่า (Starvation)

#### 4.3 โมเดล Producer-Consumer Work Queue ใน CoreSpace:
เราออกแบบระบบคิวงานแบบคู่ขนาน:
1. เธรดคนงาน (Workers) จำนวน 8 เธรด ทำงานดึงงานจาก `queue.Queue` แบบ Thread-Safe
2. เมื่อเธรดใดพบโฟลเดอร์ย่อย จะทำหน้าที่เป็น Producer ดันโฟลเดอร์นั้นกลับเข้าคิว
3. คำสั่งสำรวจไฟล์จะถูกส่งลงสู่อุปกรณ์จัดเก็บข้อมูลพร้อมกันหลายช่องทาง ผลักดันค่า Queue Depth ให้อยู่ในระดับที่ดึงความเร็วของชิป NVMe ออกมาได้อย่างเต็มที่
4. เมื่อไพทอนเรียกใช้ Win32 API ผ่าน `ctypes` การประมวลผลระดับ C จะ **ปลดล็อก Global Interpreter Lock (GIL) โดยอัตโนมัติ** ทำให้บรรลุการทำงานแบบมัลติเธรดระดับฮาร์ดแวร์อย่างแท้จริง

### เสาหลักที่ 5: การลดภาระ System Call Overhead ด้วย LARGE_FETCH
*(อ้างอิง: หนังสือ Silberschatz บทที่ 2 Operating-System Structures)*

```text
เปรียบเทียบการข้ามขอบเขต Ring 3 (User) <-> Ring 0 (Kernel):

แบบดั้งเดิม (Standard Buffer 4KB):
[User Mode]   ──(NtQueryDirectoryFile)──> [Kernel Mode] (คืนค่ามาได้ ~30 ไฟล์)
[User Mode]   ──(NtQueryDirectoryFile)──> [Kernel Mode] (คืนค่ามาได้ ~30 ไฟล์)
(สลับโหมดซ้ำไปซ้ำมานับหมื่นรอบ เกิด Context Switch Overhead สะสม)

แบบ CoreSpace (LARGE_FETCH Buffer 64KB):
[User Mode]   ──(NtQueryDirectoryFile)──> [Kernel Mode] (คืนค่ามาเป็นก้อนใหญ่ ~500 ไฟล์ในรอบเดียว!)
(ลดจำนวนรอบการสลับข้ามโหมดลงมากกว่า 10 เท่า)
```

#### 5.1 คอขวดของ User-to-Kernel Mode Context Switches:
ทุกครั้งที่มีการเรียกใช้คำสั่งอ่านสารบัญไดเรกทอรี โปรเซสระดับผู้ใช้ (Ring 3) จะต้องส่งคำสั่งขัดจังหวะของซอฟต์แวร์หรือเรียกใช้คำสั่งซีพียู `SYSCALL`/`SYSENTER` เพื่อกระโดดเข้าสู่ Ring 0  
กระบวนการนี้บังคับให้สถาปัตยกรรม CPU ต้อง:
* บันทึกค่าสถานะรีจิสเตอร์ของกระบวนการเดิม
* ตรวจสอบความถูกต้องของพารามิเตอร์เพื่อความปลอดภัย
* สลับสแต็กหน่วยความจำจาก User Stack เป็น Kernel Stack
* อาจเกิดปัญหา Translation Lookaside Buffer (TLB) Invalidation

#### 5.2 การแก้ไขด้วย Extended Win32 API:
เราปรับใช้ฟังก์ชันเคอร์เนล `FindFirstFileExW` ร่วมกับ 2 แฟล็กสำคัญ:
1. **`FIND_FIRST_EX_LARGE_FETCH` (ค่า 0x02):** สั่งให้เคอร์เนลขยายขนาดบัฟเฟอร์การค้นหาภายใน (Internal Search Buffer) จาก 4KB เป็น **64KB** ทำให้การสลับเข้าสู่เคอร์เนล 1 ครั้ง ดึงข้อมูลระเบียนไฟล์กลับมาได้เป็นก้อนใหญ่ ลดจำนวน Context Switches ลงมหาศาล
2. **`FindExInfoBasic` (ค่า 0x01):** สั่งให้เคอร์เนลไม่ต้องสืบค้นชื่อไฟล์สั้นแบบดั้งเดิม 8.3 DOS Names (เช่น `PROGRA~1`) ลดภาระการแปลงสตริงของไดรเวอร์ระบบไฟล์ลงอย่างเด่นชัด

## 🎯 หมวดที่ 4: แนวทางการตอบคำถามกรรมการสอบ (Technical Defense Q&A)

คำตอบต่อไปนี้ต้องปรับให้ตรงกับโค้ดและผลทดสอบของเวอร์ชันส่งงานก่อนใช้พูดจริง รายการต้นแบบ Win32 ข้างต้นมีไว้ศึกษาประวัติการออกแบบ

### ❓ คำถาม: "ทำไมถึงเรียกขนาดเนื้อหาไฟล์ว่า Logical Size และทำไมมันไม่เท่ากับ Size on Disk?"
> **คำตอบเชิงเทคนิค:**  
> "Logical Size คือขนาดเนื้อหาตาม metadata ของไฟล์ ส่วน Allocated Size คือจำนวนไบต์ที่ Windows รายงานว่าจัดสรรให้ไฟล์ ค่าต่างกันได้จากการจัดสรรหน่วย การบีบอัด หรือ sparse data เราจึงวัดสองค่าจาก API ที่ระบุใน SPEC และไม่ใช้สูตรปัด cluster เป็นค่าจริงของทุกไฟล์"

### ❓ คำถาม: "การใช้ Multi-threading สแกนดิสก์ มีโอกาสติด Deadlock ไหม และแก้ปัญหาอย่างไร?"
> **คำตอบเชิงเทคนิค:**  
> "ต้นแบบใช้คิวและ worker threads เพื่อแบ่งงาน แต่รูปแบบนี้ไม่ได้รับประกันว่าปลอด deadlock หรือเร็วกว่าเสมอ เวอร์ชันส่งงานจะทดสอบการจบงาน การยกเลิก และข้อผิดพลาดจริง พร้อมเปรียบเทียบเวลาบน fixture เดียวกันก่อนกล่าวอ้างเรื่องความเร็ว"

### ❓ คำถาม: "การใช้ Python มีปัญหาติดเรื่อง GIL (Global Interpreter Lock) หรือไม่ แล้วทำไมถึงเร็วได้?"
> **คำตอบเชิงเทคนิค:**  
> "เป้าหมายใหม่ให้โปรแกรม C/POSIX เป็นแกนเดินไฟล์ ส่วน Python เป็นตัวเชื่อมเว็บและอ่านผล การตอบสนองของหน้าเว็บแยกจากเวลาสแกนด้วยงานเบื้องหลัง เราจะรายงานเวลาและหน่วยความจำที่วัดจริง ไม่อ้างว่า GIL หรือ NVMe queue depth เป็นเหตุให้เร็วโดยไม่มีการวัด"
