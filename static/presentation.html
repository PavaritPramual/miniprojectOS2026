บทพูดหน้า 2

OS ช่วยให้เรารู้ว่าไฟล์ใดใช้พื้นที่มาก **ธีรเมธ · 40 วินาที** เมื่อไฟล์กระจายหลายโฟลเดอร์ เราอาจไม่รู้ว่าอะไรใช้พื้นที่มาก CoreSpace แปลงข้อมูลที่ OS อ่านได้เป็นเมืองไฟล์ครับ พื้นที่ฐานอาคารใช้เทียบสัดส่วนขนาดในมุมมองนี้ เลือกอาคารแล้วชื่อและขนาดค้างอยู่ด้านข้าง ถ้าไฟล์เล็กจนหาไม่เจอ สามารถค้นจากผลสแกนทั้งหมดได้ ภาพนี้มาจาก C และ Python อ่านไฟล์จริงในโปรเจกต์บน Windows ต่อไปศรัณย์จะอธิบายว่าเราอ่านข้อมูลนั้นได้อย่างไรครับ ชี้พื้นที่ฐาน ไม่ใช้ความสูงอาคารเป็นสเกลไบต์โดยตรง เพราะความสูงใช้ log หน้าต่างเป็นการตกแต่ง ไม่ใช่จำนวนไฟล์ สีใช้ช่วยแยกประเภทตามนามสกุล ดูชื่อประกอบได้ รายการที่เป็นศูนย์หรือไม่ทราบขนาดยังแสดงในส่วนแยก ไม่สมมติพื้นที่ให้มัน หลักฐาน: docs/results/UX_CITY_UAT.md; docs/results/READABLE_FILES_FIX.md; docs/results/REAL_SCANNER_INTEGRATION.md

บทพูดหน้า 3

อ่านขนาดไฟล์ได้โดยไม่ต้องอ่านเนื้อหาทั้งไฟล์ **ศรัณย์ · 60 วินาที** ระบบไฟล์จัดเก็บชื่อและรายการใน directory ส่วนข้อมูลเกี่ยวกับไฟล์ เช่น ชนิดและขนาด เรียกว่า metadata ครับ โปรแกรมของเราเดินอ่านโฟลเดอร์และโฟลเดอร์ย่อย แล้วอ่าน metadata ของแต่ละรายการ ขนาดเนื้อหาอ่านจาก st_size จึงไม่ต้องเปิดอ่านเนื้อหาทั้งไฟล์เพื่อรู้ขนาด ข้อมูลนี้นำมาสร้าง tree และรวมขนาดของโฟลเดอร์ได้ครับ ใช้ child-001.txt จาก fixture แบบ VariedSizes มี st_size 1,024 ไบต์ประกอบ แยก tree ที่เราแสดงออกจากการจัดเก็บภายในของระบบไฟล์ ไม่บอกว่า tree บนเว็บคือโครงสร้างบนดิสก์ทั้งหมด หลักฐาน: docs/results/UX_CITY_UAT.md; docs/results/READABLE_FILES_FIX.md; docs/results/REAL_SCANNER_INTEGRATION.md

บทพูดหน้า 4

โปรแกรม C ขอข้อมูลไฟล์ผ่าน POSIX API **ศรัณย์ · 70 วินาที** ใน C เราใช้ opendir เปิด directory ใช้ readdir อ่านรายการ แล้วใช้ lstat อ่านชนิดกับขนาด โดย lstat ไม่ตาม symbolic link ไปยังปลายทาง เมื่อใช้เสร็จจะปิดด้วย closedir ครับ ถ้ามีข้อผิดพลาด โปรแกรมส่งเหตุผลกลับ ไม่ตีความว่าเป็นขนาดศูนย์ ลิงก์ที่ชี้กลับโฟลเดอร์เดิมจะถูกข้าม เพื่อป้องกันการเดินวนไม่จบ ชื่อเหล่านี้เป็นส่วนติดต่อ POSIX ผ่านไลบรารีระบบ ไม่ได้แปลว่าการเรียกทุกฟังก์ชันตรงกับ kernel system call หนึ่งครั้ง การขอข้อมูลจาก kernel เกิดอยู่ภายในส่วนนี้ครับ ต่อไปปวริศช์จะอธิบายว่า Python รับผลจาก C อย่างไร โชว์โค้ดจริงช่วงสั้น ๆ จาก `scanner/diskviz-scan.c` เน้นบรรทัดสำคัญ ห้ามบอกว่ามีผล strace ยืนยันแล้วหากยังไม่ได้เก็บหลักฐาน หลักฐาน: docs/results/UX_CITY_UAT.md; docs/results/READABLE_FILES_FIX.md; docs/results/REAL_SCANNER_INTEGRATION.md

บทพูดหน้า 5

Python กับ C เป็นคนละ process และส่งข้อมูลผ่าน pipe **ปวริศช์ · 70 วินาที** เว็บส่งคำขอผ่าน HTTP ให้ Python บน Windows จากนั้น Python เปิดโปรแกรม C ใน Ubuntu ผ่าน WSL ซึ่งยังอยู่บนคอมเครื่องเดียวครับ C กับ Python เป็นคนละ process จึงส่งข้อมูลกันผ่าน pipe โดย C เขียน stdout ทีละบรรทัดเป็น NDJSON และ Python อ่านเพื่อตรวจและบันทึกลง SQLite งานสแกนทำเบื้องหลัง เว็บจึงขอสถานะและรายการได้ระหว่างรอ เมื่อกดยกเลิก Python ส่ง TERM ไปยัง PID ของโปรแกรมใน Ubuntu ถ้าจำเป็นจึงใช้ KILL และตรวจว่าหยุดจริงก่อนรายงาน cancelled ไม่ใช่แค่หยุดถามสถานะบนเว็บครับ ชี้ลูกศร HTTP กับ pipe คนละเส้น แยก background thread ของ Python ออกจาก process ของ C ไม่อ้างว่ามีอัลกอริทึม CPU scheduling ใหม่ หลักฐาน: docs/results/UX_CITY_UAT.md; docs/results/READABLE_FILES_FIX.md; docs/results/REAL_SCANNER_INTEGRATION.md

บทพูดหน้า 6

ขนาดเนื้อหากับพื้นที่ที่ใช้บนดิสก์อาจต่างกัน **ปวริศช์ · 60 วินาที** Logical คือขนาดเนื้อหาจาก metadata ที่ C อ่าน ส่วน Allocated ใช้ GetCompressedFileSizeW ของ Windows วัดครับ สองค่านี้อาจต่างกันจากวิธีจัดเก็บ เช่น ไฟล์บีบอัด แต่ไฟล์ตัวอย่างที่ตรวจในงานนี้ zero.bin ได้ศูนย์ทั้งสองค่า และ large.bin ได้ 1,048,576 ไบต์ทั้งสองค่า ซึ่งตรวจเทียบกับ Windows API อีกวิธีแล้ว ยอดโฟลเดอร์รวมไฟล์ที่อ่านได้ทั้งหมด ไม่ใช่เฉพาะ 50 แถวที่เห็น ค่าศูนย์หมายถึงวัดได้ศูนย์ ส่วน null หมายถึงยังไม่ทราบหรือวัดไม่ได้ และยอดนี้อาจไม่เท่าพื้นที่ใช้ทั้งไดรฟ์ เพราะรายการที่อ่านไม่ได้ ข้อมูลระบบ และ hard link ครับ ต่อไปจะเปิดโปรแกรมให้ดูจริง คำอธิบาย compressed/sparse เป็นทฤษฎี ไม่อ้างว่าได้ทดสอบกับไฟล์ชนิดนั้นแล้ว ไม่ใช้ Allocated ลบ Logical เป็น Slack เสมอ หลักฐานขนาดอยู่ใน [ผลรวมระบบ](results/REAL_SCANNER_INTEGRATION.md) หลักฐาน: docs/results/UX_CITY_UAT.md; docs/results/READABLE_FILES_FIX.md; docs/results/REAL_SCANNER_INTEGRATION.md
